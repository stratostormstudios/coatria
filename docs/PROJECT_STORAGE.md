# Project files and Runpod storage

Coatria stores the folder catalog in Neon and file bytes on an existing Runpod network volume. Each Studio project has its own **Project files** tab. Company administrators connect an existing volume, bind it to a project, and preview an additive production folder plan. Users with company membership can browse and download verified files; administrators can upload and organize them. External agents need separately approved `storage.read`, `storage.write`, and/or `storage.organize` grants and a current run lease. Existing agents do not inherit these grants. Model-history projections omit transfer tokens, Authorization headers and access URLs; only the trusted worker receives the raw temporary transfer capability.

This implementation does not purchase a volume or start compute. Runpod S3 credentials are separate from the Runpod compute API key. Enter them only in the company storage connection form or through a secure server request. The application encrypts credentials using `COATRIA_HOSTING_KEYRING`, binds the ciphertext to the company and connection, and never sends them to browsers or models. Use dedicated Runpod credentials/account appropriate to the company: Runpod does not currently offer S3 bucket policies or ACLs to enforce these project boundaries itself.

## What is stored

- Logical folders, names, parent relationships and catalog revisions are independent of production task revisions.
- A file can have multiple immutable versions. Every version gets a server-created opaque object key under `coatria/companies/{companyId}/projects/{projectId}/objects/{versionId}`.
- Renaming or moving a file/folder changes its catalog entry, not the underlying objects or version identity.
- A completed multipart upload is initially **verifying**. A separate worker reads the stored bytes and computes SHA-256; only then can the version become **ready** and receive download access. Storage verification is not media QC, client approval, or delivery.
- Provider ETags pin subsequent reads to the verified stored object. This is application-level immutability; Runpod does not offer object lock/versioning. An external administrator can alter the volume, so replaced objects must fail access and be re-imported as new versions.

## Transfer service

Runpod's documented S3 compatibility does not include presigned URLs. Large bytes must bypass Vercel's function payload limit. `scripts/storage-gateway.ts` is a separate long-running Node service that streams between a browser/external worker and Runpod. Its verification queue is persisted in PostgreSQL. A process restart retries only read/hash verification, never uncertain provider writes.

Build with `docker build --platform linux/amd64 -f scripts/hosting/StorageGateway.Dockerfile -t coatria-storage-gateway:<release> .`. The image uses the same reviewed pinned Node image as the managed worker. Run behind authenticated transfer endpoints on a dedicated HTTPS origin, for example an operator-controlled `files` subdomain; use TLS termination, private database connectivity and a secrets manager. Do not expose the raw port publicly. Run as non-root with a read-only filesystem and a memory limit. No local disk is required for uploads.

Gateway configuration: `DATABASE_URL`, `COATRIA_HOSTING_KEYRING`, `APP_URL`, `HOST`, and `PORT`. Use a dedicated least-privilege database identity, not the database owner. The gateway needs the grants in `database/storage-gateway-permissions.sql` after the role has been created by the database administrator. Its credential vault keyring must match the application. The service processes at most eight concurrent HTTP transfers and one stored-byte verifier per instance. Scale gateways behind a load balancer only after testing concurrent behavior and database/provider capacity.

Before starting this candidate gateway, run `node --import tsx scripts/storage-gateway.ts --preflight` with its private service configuration. Both preflight and normal startup require the actual `coatria_storage_gateway_v1` LOGIN, matching current/session identity, migration ledger 001–034 and the exact effective grants in the shipped permissions script. Owner/application credentials, `SET ROLE` impersonation, elevated roles, role memberships, unexpected ownership/schema creation, widened column or PUBLIC grants, grant options, sequence access and callable non-system SECURITY DEFINER functions fail closed. Preflight closes its database pool without listening, polling verification or contacting a provider; normal startup runs the same checks before serving. This is a point-in-time database/configuration check, not live S3, TLS or host qualification. As of 2026-09-20, production source `41bbaf0` is still at migration 033: migration 034 and this gateway startup requirement are pending candidate validation and rollout; do not start the new gateway against that older ledger.

Application configuration: set `COATRIA_STORAGE_GATEWAY_URL` to its exact HTTPS origin and `COATRIA_STORAGE_GATEWAY_ENABLED=true` **only after** the deployed service passes a live Runpod conformance test. CSP then permits that single origin. Without both, uploads/downloads are visibly unavailable and their API fails closed. Folder organization still works. A configured URL is not a live health proof.

## Transfer protocol

1. `POST /api/companies/{companyId}/studio/projects/{projectId}/files/uploads` reserves a version using a unique `clientId`, current catalog `revision`, optional `fileId` for a new version, `parentId`, `name`, `bytes`, `contentType`, and optional expected `sha256`. Save these exact reservation arguments until completion. An exact retry obtains a fresh short-lived grant for the same upload, even after the reservation advances the catalog revision.
2. The response includes `upload.baseUrl`, `token`, `partBytes`, and `expiresAt`. Keep the token in memory and use `Authorization: Bearer ...`; never put it in a query string or persistent browser storage.
3. `POST {baseUrl}/start` with `{}` initializes multipart storage once. `GET {baseUrl}` returns durable status and completed part receipts. Do not reissue an uncertain provider action.
4. `PUT {baseUrl}/parts/{number}` streams each exact part with its declared Content-Length. Parts are 64 MiB, except the final part. A replay consumes and hashes the supplied part, and succeeds only if it matches the original receipt.
5. `POST {baseUrl}/complete` with `{}` enters asynchronous verification. Poll status until **ready** or a terminal error. `POST {baseUrl}/cancel` stops a confirmed incomplete upload; an unknown provider initiation cannot be reported as cancelled. No API deletes verified originals.
6. `POST .../files/versions/{versionId}/access` returns `access.url` and temporary Authorization headers for a verified download. File access is checked at issuance, on each operation, periodically during long reads, and after verification. A revoked connection or ended agent lease stops access. The browser streams to a chosen local file where supported; its fallback is limited to 128 MiB and does not buffer large footage into memory.

The initial application limit is 100 GiB per file, eight active upload sessions per company, and a 24-hour upload lifetime. Human transfer grants last up to two hours; agent grants last 15 minutes and are also tied to the exact agent credential and live run lease. The client must renew an expired grant using the original reservation; a changed `clientId` is a different upload. Agent tool receipts can contain a short-lived transfer capability; a new request is needed when that receipt's capability expires. Uncertain operations are surfaced for reconciliation, not silently retried. Unverified/cancelled objects may remain on the volume pending explicit operator reconciliation; automatic destructive cleanup is not implemented.

Agent tools expose the same catalog, plan, organization, reservation and access operations. The tools do not pass file bytes into model context, upload private files to Higgsfield, send client messages, buy resources, or approve media. Those require their own explicit workflow and permissions.

Raw-ticket agent calls (`storage_upload_reserve` and `storage_file_access`) require `X-Coatria-Storage-Transport: 1`. Missing or unsupported versions fail with `409 STORAGE_TRANSPORT_UPGRADE_REQUIRED` before creating or returning a ticket; this header does not grant storage permission or replace a current run lease. A conforming external integration must retain tokens, authorization headers and access URLs only in its trusted transport and apply the bounded `modelContextResult` projection before persisting or sending model history. Upgrade both `agent-worker.mjs` and `provider-adapter.mjs` together; the adapter requests this protocol explicitly and refuses an older worker before inference. Updating only the worker does not opt an older adapter into raw tickets. Existing commit-pinned hosts require a new reviewed release before granting them file-transfer work. The managed inference broker independently projects stored receipts and replayed history; trusted in-process calls preserve the unmodified transport result. The generic MCP bridge does not opt in to raw tickets.

## Production activation gate

Before claiming live file storage, test the selected Runpod volume with synthetic content: multipart create/upload/complete, streamed read and SHA-256 match, conditional ETag reads, byte ranges, restart/resume, cancellation, revocation, and independent tenant rejection. Range support is experimental until this is confirmed on the actual region. Unit and database fixtures do not prove provider compatibility. Verify actual storage capacity, retention/backup policy, account billing and TLS ingress. Volumes persist and can keep incurring charges with no compute pod; a volume is not a backup.

Official references: [Runpod S3 API](https://docs.runpod.io/storage/s3-api), [network volumes](https://docs.runpod.io/storage/network-volumes), [Runpod pricing](https://www.runpod.io/pricing), [Vercel function limits](https://vercel.com/docs/functions/limitations). Pricing and region availability are provider-controlled; no recurring purchase is made by this feature.

## Generated-output archives

[Higgsfield archives](HIGGSFIELD_ARCHIVES.md) can prepare one exact adopted output for an approved storage destination. A separate worker performs decode and stored-byte verification; its archive uploads are excluded from the ordinary browser-upload verification queue. The feature is disabled until its dedicated role, storage transport and decoder isolation are qualified. It neither purchases a volume nor modifies retained inference storage.
