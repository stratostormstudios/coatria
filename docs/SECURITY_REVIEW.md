# Coatria security review — 2026-09-08

This is an implementation review and regression-test record for Coatria's first security update. It covers application authorization, browser state and capture, integration clients, database privileges, dependencies and release controls. Severity below describes the affected Coatria boundary; it is not a CVSS assessment or evidence that an issue was exploited in production. This work is not an independent penetration test or a security certification.

## Corrected application and runtime issues

These changes are implemented in the reviewed and deployed source, with regression evidence recorded above. Open operational controls are listed separately below.

| ID / scoped severity | Trigger and impact | Implemented correction and regression coverage |
| --- | --- | --- |
| DB-01 — High, excessive application database privileges | The original runtime login `neondb_owner` had effective CREATEROLE, CREATEDB, BYPASSRLS, public-schema CREATE and users-table TRUNCATE privileges. A compromise of application database access therefore carried administrative/destructive powers beyond normal requests. | The new deployment uses `coatria_runtime_v1`; those capabilities were verified false. Explicit table/column grants, PostgreSQL denial tests, pooled login and live application checks validate the replacement. Owner aliases were removed from project configuration while Neon data was preserved. Historical deployments may still retain the earlier owner credential, so that residual exposure remains an open gate below. |
| AUTH-01 — High, invitation recipient authorization | A holder of an email-restricted invitation could claim its intended email during unverified registration. The address alone did not prove control of that mailbox. | Restricted invitations now require server-recorded email verification. Public verification delivery is absent, so unverified email restrictions fail closed. Hiring acceptance binds the invitation to the reviewed account UUID. Tests cover legacy restricted links, forged profile fields and redemption by another account. |
| AUTH-02 — High, offboarding and role restoration | An invitation issued before removal could restore a former member's access. Concurrent redemptions could also overwrite the role accepted first. | Memberships retain an access-revocation timestamp; older invitations cannot restore access. Company and account/invitation locking coordinates joins with offboarding and simultaneous joins. A new invitation issued after removal remains usable. Tests exercise both sequential and concurrent cases. |
| WORK-01 — Medium, integrity of independent approval | Saving an already submitted review or reopening/resubmitting work could replace the recorded submitter and let an earlier author appear independent. The current release has no automated payments or financial reward execution. | A persistent author set survives review cycles; review saves do not relabel the submitter. Approval excludes recorded authors, the assignee, submitter and relevant agent sponsors. Tests require an uninvolved administrator for final acceptance. Migration 004 backfills authors still represented in tasks and agent contributions; it cannot reconstruct history that was never stored. |
| AUTH-03 — Medium, company-agent sponsorship | A demoted administrator could offer a company agent to a new opening based only on being its creator. | Applications recheck and lock the sponsor's current owner/admin membership and the agent's active state. A regression case rejects a demoted sponsor. |
| UI-01 — Medium, privacy within a shared browser | Another tab could replace the shared session cookie while an old tab retained a private draft, pending export or logout action. | Requests carry the UI's expected account ID; the server rejects mismatches. Account changes reset private UI state and invalidate delayed results/exports. Tests cover wrong-account writes/logout, draft cleanup and late downloads. The header is a stale-state guard, not an authentication credential; the session cookie remains authoritative. |
| UI-02 — Medium, workspace state isolation | An old company's delayed mutation could refresh or replace the newly selected company's view. | Workspace callbacks and refreshes remain bound to their selected company; old continuations are discarded. Browser tests hold and release an old presence write after a company switch. This addresses client state confusion, not a demonstrated server-side tenant authorization bypass. |
| AUTH-04 — Medium, password resistance | Existing hashes used the lower Node scrypt default profile. | New hashes use a versioned `N=32768, r=8, p=3` profile with random salts and bounded accepted encodings. Successful legacy login upgrades the hash without changing the password or revoking unrelated sessions. Tests cover incorrect passwords, unsupported cost encodings and simultaneous legacy logins. Accounts that do not log in retain their legacy hashes until upgraded. |

The password profile is one of OWASP's documented scrypt CPU/memory tradeoffs. This is a work-factor improvement, not a claim that password-only authentication provides MFA. [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

## Additional hardening and verified boundaries

- **Content Security Policy:** production HTML uses a fresh script nonce, `strict-dynamic`, disabled inline script handlers, no `unsafe-eval`, blocked framing and a restricted base URI. Browser checks inject an untrusted parser script and handler and confirm neither executes. Inline styles remain allowed for React/3D geometry. Development intentionally permits eval for development tooling. This adds defense in depth; the review did not establish an existing exploitable XSS. [Next.js CSP guidance](https://nextjs.org/docs/app/guides/content-security-policy).
- **Integration destinations:** agent and storage clients accept HTTPS origins, with loopback HTTP for local tests, and reject redirects. Tests prove that a redirected destination receives no follow-up request and that client output omits tokens. This closes destination ambiguity; it is not evidence that a cross-origin bearer token was previously leaked. The storage connector's real-process test also excludes outside junctions, hidden files, file contents and absolute paths from its metadata manifest.
- **Media lifecycle:** authenticated signaling enforces company/room membership and recipients, capacity and expiry. Capture stops on leave, terminal authorization failure or a 45-second authorization-refresh failure. Late screen-picker results cannot attach to another call. Synthetic-media checks cover packets, frames, cleanup and revocation; they do not establish WAN/TURN reliability or every operating-system picker behavior.
- **Dependency supply chain:** the reviewed lockfile had 118 package entries with npm-registry resolutions and integrity metadata. Full `npm audit` reported zero known vulnerabilities at the time of review; registry signature verification passed for 59 installed packages and 32 attestations. These are dated registry results, not a guarantee against undisclosed vulnerabilities or malicious dependency behavior.
- **CI execution:** the workflow has read-only repository permissions, a time limit, no persisted checkout credentials, complete history scanning before dependency installation, an audit gate, PostgreSQL tests, type checking and a production build. It pins the PostgreSQL 17 image by digest and official, signature-verified [checkout v7.0.1](https://github.com/actions/checkout/releases/tag/v7.0.1) and [setup-node v7.0.0](https://github.com/actions/setup-node/releases/tag/v7.0.0) commits. Both actions declare Node 24 runtimes; application checks still use Node 22.
- **Secret scanning:** the scanner checks the working tree, staged blobs and complete reachable Git history, including recognized credentials inside binary-looking files. Tests cover staged-only and deleted historical secrets, nested environment files and redacted failure output. The review scan found no recognized provider credentials in the repository or reachable history. Pattern scanning does not prove every possible secret format is absent and does not sanitize conversation history or provider deployment snapshots.

Relevant sources: [CSP browser test](../tests/browser/csp.spec.ts), [integration-client boundaries](../tests/client-boundaries.test.ts), [media harness](../tests/room-call-browser.mjs), [secret-scanner tests](../tests/secret-scanner.test.ts), and [CI workflow](../.github/workflows/ci.yml).

## Production database separation

The production project is configured for `coatria_runtime_v1`, with `LOGIN`, `NOINHERIT`, `NOSUPERUSER`, `NOCREATEROLE`, `NOCREATEDB`, `NOREPLICATION` and `NOBYPASSRLS`. Pooled authentication, restricted privileges and 39 live API checks through the new READY deployment have been verified. The role receives explicit application table/column grants and reads migration status. PostgreSQL CI verifies denied verification/migration writes, table truncation and schema/role creation. The checked grant file also clears old users-column grants before reapplying permitted columns.

For first-time setup only, use the explicit operator-only [provisioning helper](../scripts/provision-runtime-role.mjs) after applying all numbered migrations. Production already has this role. The helper accepts `{connectionString,password}` through JSON stdin, requires an owner with role-creation authority, verifies TLS for direct Neon endpoints, refuses an existing role, shares the migration lock, applies grants transactionally and reports only metadata. It checks effective privileges, including unwanted PUBLIC grants. A failed or ambiguous COMMIT must be investigated; do not assume a safe automatic retry. Ordinary builds and migrations do not invoke this helper. Routine releases must not recreate the login: after future migrations, an owner applies any updated explicit [runtime grants](../database/runtime-permissions.sql) and verifies required and denied privileges.

Neon documents that SQL-created roles do not automatically join `neon_superuser`, unlike roles created through its console/API. `NOINHERIT` alone does not negate privileges granted to PUBLIC; effective privilege checks are therefore required. The users-column UPDATE grants support the API's row-lock statements without allowing direct updates to its verification field. [Neon role behavior](https://neon.com/docs/reference/compatibility), [PostgreSQL SELECT privileges](https://www.postgresql.org/docs/current/sql-select.html), [PostgreSQL schema privileges](https://www.postgresql.org/docs/current/ddl-schemas.html).

The configuration cutover preserved Neon `coatria-production`, its database and data. Automatic environment-variable injection was detached from the Vercel project and owner-credential aliases removed. The project now contains only **production-only sensitive Secret `DATABASE_URL`** for the runtime connection and plain `APP_URL=https://coatria.com`; no production database credential is configured for preview. Future numbered migrations use a direct owner connection obtained separately from the Neon dashboard for the operator's migration process, never an owner alias stored in the deployed application. Secret values are write-only after saving; this does not remove their availability to the running application. [Vercel Secret environment variables](https://vercel.com/docs/environment-variables/sensitive-environment-variables).

Read-only Vercel inspection found no Git repository connection and reported `ssoProtection: all_except_custom_domains`. Non-custom deployment URLs are configured for Vercel authentication; the public custom domain remains available as intended. This setting does not revoke credentials in old deployment snapshots or establish GitHub branch protection. [Vercel Authentication](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication).

The project custom-WAF configuration request returned HTTP 404, so no custom configuration was available to review. This does not mean the service has no firewall coverage: Vercel provides automatic platform DDoS mitigation. Application-specific abuse, costly signup/login traffic, polling budgets, spend limits and alerts still need operational validation before broader exposure. [Vercel DDoS mitigation](https://vercel.com/docs/vercel-firewall/ddos-mitigation).

The runtime role still has global application DML and can update password hashes because account password changes require it. Tenant isolation and private-vault access remain application-enforced; there are no per-tenant PostgreSQL RLS policies. A runtime credential or SQL-injection compromise can therefore still compromise application data and identities. Least privilege here reduces administrative powers; it does not make the database an independent tenant security boundary.

| Required before broad commercial scale | No independent penetration test, representative load test, backup restore drill or measured regional recovery objectives have been completed. Vercel stores environment values in deployments; changes apply to new deployments and do not rewrite old ones. Credential rotation must account for those historical deployments. [Vercel secret rotation](https://vercel.com/docs/environment-variables/rotating-secrets). GitHub branch protection can enforce reviews and checks only once configured for the branch; a workflow file alone does not enforce a merge gate. [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
