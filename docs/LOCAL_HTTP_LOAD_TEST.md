# Local HTTP connection test

Run from the repository with dependencies installed:

```sh
node scripts/load-office.mjs --clients 50 --duration 30
```

The test starts its own Next development server on `127.0.0.1:4196` and creates an ephemeral PGlite database on a dynamically assigned loopback port. Next runs from a dedicated `.devdata/load-<uuid>` source copy, where its generated TypeScript files and `.next-load` output cannot overwrite the active checkout. Only src/public/package/Next/TS sources are copied; `.env`, `.git`, `.vercel` and purchased `.runtime-assets` are excluded. Installed dependencies are shared through a temporary link, which is unlinked after stopping the server. It refuses an occupied HTTP port, execution from a deployed production process, remote targets and existing app databases. Optional flags are `--clients` (2–50), `--duration` (10–60 seconds), `--port`, `--mode` (`development` or `production`) and `--report` (a new JSON file). It never loads credentials for seeding from an environment file or changes a running application's database.

For genuine PostgreSQL, explicitly set `COATRIA_LOAD_DATABASE_URL` in the invoking process to a loopback PostgreSQL service and an empty database named `coatria_load_<suffix>`. Query options and other database names are refused. The harness checks that the public schema is empty before any migration or fixture write; it does not create or drop databases. `--mode production` builds the app into `.next-load` and starts that isolated production build. The public-source CI scale job provisions its own PostgreSQL 17 service with a run-specific database name, runs 50 sessions for 60 seconds, and uploads the sanitized report. Purchased assets are not included or exercised.

Each test participant has a different user ID and opaque authenticated cookie. Fixture accounts, hashed sessions and tasks are inserted directly into the isolated database; all measured collaboration uses real HTTP requests through Next route handlers. This measures authenticated collaboration, not signup or password hashing. Fixture credentials, emails, company IDs and message contents are never written into the report.

The company uses the shipped `OFFICE_50_PRESET`: a 30 × 20 m floor with 148 furniture items. Movement updates cycle through its audited standing approach points, so workspace responses include the real floor payload. Report environment metadata includes `floor`, `layoutItems` and `uniqueAssetCount`; it contains no model binaries. The earlier development/PGlite report with an empty floor is a historical baseline and does not represent this final workload.

The workload has independent non-overlapping request loops per participant: movement writes every second, presence reads every 2 seconds, full workspace reads every 5 seconds, and session reconciliation every 15 seconds. Movement matches the office's sustained one-second movement updates and does not trigger another full workspace read. Participants concurrently submit chat messages and update assigned tasks. Three sessions verify visibility of every change and the last acknowledged positions. Additional checks cover tenant isolation, stale identity headers, expired authentication, real 45-second presence expiry and reconnect without duplicate occupants. Expiry verification adds about 47 seconds after the measured traffic interval.

Reports default to `../output/coatria-load/connections-<timestamp>.json`. The UI may import the report as evidence of actual local connections; it must retain its environment label and limitations. `correctnessPassed` summarizes correctness, security and cleanup checks; `performancePassed` requires zero unexpected errors and p95 latency at or below the explicit 1,000 ms test budget. `passed` requires both. This budget is a release test target, not a production guarantee. Latency is measured from HTTP dispatch until the response body is consumed, excluding initial route compilation. Summary percentiles and throughput apply only to the measured traffic interval; `verificationRequests` counts the other authenticated HTTP checks.

The versioned report has `schemaVersion: 1`, `kind: "coatria-connections"`, `generatedAt`, `summary`, `checks`, `environment`, `policy`, per-operation `metrics`, and `cleanup`. Summary includes `clients`, `durationSeconds`, `requests`, `unexpectedErrors`, `errorRate` (0–1), `p50Ms`, `p95Ms`, `maxMs`, `requestsPerSecond`, `bytesReceived`, `passed`, `verificationRequests`, and `wallClockSeconds`. Each check has `id`, `label`, `passed`, and `detail`.

PGlite uses one database connection; genuine PostgreSQL uses the application's normal five-connection pool. The report identifies which ran and whether Next was in development or production mode. An emulator run does not establish real PostgreSQL lock behavior. Neither configuration establishes Vercel capacity, global network latency, avatar rendering performance, asset download performance or WebRTC capacity. Run the PostgreSQL CI suite for database concurrency and privilege checks. A geographically distributed production benchmark requires a separate authorized environment and plan.

The harness stops only its own server process, removes exact fixture IDs and closes its database connection. The PGlite database disappears; the dedicated PostgreSQL database retains its migrated empty schema until its owner or CI service disposes of it. It unlinks only the verified temporary dependency link and never recursively removes installed dependencies. The owned `.devdata/load-<uuid>` source/build copy is retained for inspection and may be removed manually when no load run is active. Root TypeScript configuration should exclude `.devdata` so its temporary copies are not part of a normal source typecheck.

## Investigating latency

Use `--diagnostics true` with the isolated PostgreSQL fixture to collect bounded timing evidence. It is off by default and enabled in the CI scale job. The diagnostic run keeps the same participants, warmup, polling cadence, five-connection application pool, 60-second CI interval and 1,000 ms p95 target. Its original HTTP latency and correctness fields keep their original meaning; `diagnostics.requiredCoverage.passed` is a separate CI requirement. Missing telemetry cannot turn a failed load test into a pass.

The server is started with an explicit test-only Node preload. It measures pool acquisition and query durations, pool occupancy, process CPU and event-loop delay, and sends aggregate records through a private child-process pipe. It does not add an application endpoint or modify production request handlers. The report also records client scheduling/response phases and event-loop delay, bounded PostgreSQL activity/wait counts, and available host CPU, memory, pressure and cgroup counters. Records exclude SQL text, query parameters, credentials, fixture identities and message bodies. Unavailable host counters are reported as unavailable rather than zero. Server windows include startup and prechecks; timestamps identify their relationship to the measured load interval.

Client requests are grouped by dispatch time; server acquisition/query durations are grouped by completion time. Query durations include driver, network and event-loop time. Pool occupancy is sampled during acquisition and at 250 ms intervals, so its sample average is not a time-weighted average. Cadence lag includes a request that outlasts its normal polling interval, while each loop continues to wait for its previous operation as before.

Compare pool acquisition time with query time and database waits before attributing a slowdown. A long pool queue with short queries indicates admission pressure; long database waits and blockers suggest database contention; long event-loop delays with little database activity suggest application or host scheduling. These are diagnostic signals, not proof by themselves. Instrumentation has overhead and shared CI hosts can vary, so retain failed runs and their exact source and environment instead of discarding failures after a successful repeat.

For example, [CI142](https://github.com/stratostormstudios/coatria/actions/runs/36832162641) on source `09ffaf1a9145e3b4244d7485d0a895daea34db2f` passed correctness with 6,594 measured requests and no unexpected errors, but failed the latency gate at p95 1,865.02 ms. The preceding [CI140](https://github.com/stratostormstudios/coatria/actions/runs/36827452279) measured 505.22 ms. Measured handlers, migrations, dependencies and the workload were unchanged; the original reports did not contain enough telemetry to determine the cause. The diagnostic option was added to investigate that failure, not to change its verdict.
