# Company runtime registry

Runtime configuration is deployment authority, not a company-admin self-service command runner. A database administrator must issue a time-bounded `platform_operator_grants` row for an existing user. That user must also currently own or administer the target company. The runtime role has no write access to the grants table. A narrowly scoped read-only definer function holds a grant row lock while checking expiry and revocation; administrative revocation therefore cannot race an admitted write.

`GET`, `POST` and `PATCH /api/operator/companies/{companyId}/runtime-configurations/{kind}` use the human session and ordinary same-origin mutation protection. Supported kinds are `managed_agent`, `archive` and `gateway`. This endpoint accepts no agent token. GET returns selection metadata only, never the raw preset, bootstrap, credentials or container environment. POST requires a UUID `clientId`, exact `expectedRevision` (zero only for the first selection), `phase`, fixed `expiresAt`, the strict reviewed `preset`, and its SHA-256 `configurationHash`. Hash the key-sorted JSON using `companyRuntimeHash`. PATCH requires a fresh UUID `clientId` and the current positive `expectedRevision`.

Managed agent presets have exactly one company and phase `service`. Trusted archive/gateway presets have exact company/project ownership and the same fixed deadline in their nested configuration, top-level preset and selection metadata. All deadlines must be between one minute and 24 hours away when committed. Bootstrap hashes, fixed images and existing preset schemas remain enforced. Secret fields and identifiable embedded credentials are rejected; encrypted provider credentials are managed separately and never belong in a preset. An operator must still review bootstrap code; a schema cannot prove arbitrary code contains no disguised secrets or unsafe behavior.

Configuration and request records are immutable. Selection revisions increase on both replacement and revocation. Replaying a request returns the original safe receipt, not authorization to use a newer configuration, and still requires current operator/admin authority. Reusing its key with changed content fails. Writes use the existing provisioning company locks. Replacement is refused while a corresponding provision is active, uncertain, stopping or needs attention. Managed worker volumes retain historical company ownership and cannot be transferred by revoking a selection. Existing CPU and inference reservations are never deleted, refunded or reset by selecting a new preset.

The internal loader returns `null` only when the company/kind has never been configured. A revoked or expired selection is retained with `enabled: false`; consumers must fail closed instead of resurrecting a deployment environment preset. Existing provision records retain the exact reviewed preset needed to reconcile and stop resources after revocation. Selecting or revoking configuration makes no provider calls and does not itself start/stop compute, mint storage access or approve spending. Provider shutdown and final invoices remain separately verified operations.

New provisioning plans bind `runtimeConfiguration` containing `configurationId`, `selectionRevision`, `configurationHash` and `expiresAt`. Legacy environment plans omit this pin. Even selecting byte-identical JSON produces a new epoch and invalidates previous plans. Consumers check this authority at approval/start, immediately before the provider submission fence, and after provider I/O. Managed host durations must fit the selected deadline. Revoked running work requests a stop using its retained provider identity and environment hashes, without requiring fresh launch credentials or an enabled preset. GET readiness resolves the target company's database selection; environment fallback exists only for a company/kind that has never had a selection. Legacy managed CPU planning uses the same historical volume ownership check.

Revocation also records `stop_requested_at` on active provisions pinned to that exact company, runtime kind and configuration ID, in the same transaction. CPU and trusted-service cron batches therefore prioritize those shutdowns over older healthy polls without waiting to rediscover the revoked selection. Provision revisions advance only when new stop intent is recorded. Archive executor revocation uses the same stop intent on its first successful revocation; replaying an old revoked credential cannot stop a later replacement. No provider operation or reservation refund occurs in the revocation transaction.

Apply migration 036 and runtime grants through the normal administrator migration process. Seed/revoke operator grants with direct parameterized administrator SQL; there is deliberately no application endpoint that creates operator authority. Test grants are synthetic and expire. Never put account credentials in a migration, source file, terminal argument, request log or review receipt.
